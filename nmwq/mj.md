##### 链表，用什么算法排序，时间复杂度是多少，空间复杂度是多少
链表排序一般采用归并排序，因为链表不支持随机访问，快排partition效率低；而归并排序可以通过快慢指针找到中点，并且合并两个有序链表只需要调整指针。时间复杂度 O(nlogn)，递归实现空间复杂度 O(logn)，如果使用迭代归并可以优化到 O(1)。

#### 为什么快排比归并快
两者平均时间复杂度都是 O(nlogn)。快速排序在实际中通常更快，主要原因是它是原地排序，空间开销小，并且partition过程连续访问数组，缓存局部性更好；同时快排常数因子通常更小。而归并排序需要额外O(n)空间，并且merge过程涉及额外的数据搬移。不过快排最坏情况是O(n²)，而归并排序稳定为O(nlogn)，因此工程实现通常会结合两者优点，例如C++ std::sort采用Introsort。

#### std::sort的原理
std::sort 常见实现采用内省排序，结合快速排序、堆排序和插入排序。
正常情况下使用快速排序进行分区；如果划分深度达到约 2log₂n，说明可能存在持续不均衡的划分，就对当前仍较大的区间改用堆排序，避免快排退化到 O(n²)。
对于足够小的区间，停止继续划分，最后统一用插入排序收尾。这样既兼顾实际效率，又保证最坏情况下 O(n log n) 的比较复杂度。

#### 虚指针大小

虚指针，也就是 `vptr`，在常见实现中是编译器放在对象内部、用于定位虚函数表的隐藏指针。它的大小通常与普通指针相同：常见的 32 位环境为 4 字节，64 位环境为 8 字节，与虚函数数量无关。增加虚函数通常增加的是虚表中的条目，不是给对象里的每个虚函数都增加一个指针。不过，多重继承时，一个对象可能包含多个 vptr，因此不能认为整个对象的虚指针开销永远只有一个指针大小。

#### vptr 和 vtable 是什么？派生类重写和不重写分别是什么情况？

`vptr` 位于对象内部，`vtable` 是通常由同类型对象共享的表，其中保存虚函数入口以及相关信息。以简单单继承为例，派生类对象构造完成后，其 vptr 指向适用于派生类的虚表：如果派生类重写了基类虚函数，对应条目指向派生类实现；如果没有重写，就保留继承来的实现。通过基类指针或引用进行普通虚函数调用时，程序根据实际对象的虚表找到最终实现。例如，`Base* p` 指向 `Derived` 对象，调用 `p->f()`，重写了就执行 `Derived::f()`，没重写就执行继承来的 `Base::f()`。重写不会修改基类对象使用的虚表，因此不会影响其他基类对象。

#### 一个基类有多个派生类时，vptr 和 vtable 是什么情况？

假设 `Base` 有虚函数 `f()`，`D1` 和 `D2` 都继承 `Base`。常见实现会分别为这些类型提供相应的虚表信息，`D1` 对象和 `D2` 对象的 vptr 指向各自类型对应的虚表。如果 `D1` 重写了 `f()`，而 `D2` 没有重写，那么通过指向 `D1` 对象的 `Base*` 调用 `f()`，执行的是 `D1::f()`；通过指向 `D2` 对象的 `Base*` 调用，则执行 `Base::f()`。各派生类的重写互不影响，同一类型的多个对象通常共享虚表，不会为每个对象复制一整张表。

#### 一个派生类有多个基类时，vptr 和 vtable 是什么情况？

以普通非虚多重继承为例，如果派生类 C 同时继承具有虚函数的 A、B，那么 C 对象内部通常包含 A、B 两个基类子对象，各自带有 vptr，分别指向适用于 C 对象的虚表部分；派生类通常与一个主要基类共享 vptr，不一定额外增加一个。如果 C 重写了某个基类的虚函数，相应虚表条目就指向 C 的实现，必要时通过调整入口修正 `this` 指针；没有重写的条目则保留继承来的实现。因此，通过 `A*` 或 `B*` 指向同一个 C 对象时，虽然两个指针的地址可能不同，但都能正确进行虚函数调用。不能简单认为“有几个基类就一定有几个 vptr”，因为非多态基类通常不需要 vptr，虚继承也会改变布局，具体由编译器和 ABI 决定。

#### C 多重继承 A、B，二者有同名虚函数时如何处理？虚继承后虚表如何布局？

假设 A、B 是两个互不相关的基类，都声明了 `virtual void f()`，C 同时继承它们且没有重写，那么直接调用 `c.f()` 存在名字查找歧义，但通过 `A*` 或 `B*` 调用可以分别选择对应的继承分支；也可以用 `c.A::f()` 显式指定，不过这种限定调用会绕过虚派发。如果 C 定义了 `void f() override`，就能同时重写两边的虚函数。常见非虚多继承布局中，A、B 的多态子对象分别具有 vptr，必要时通过调整入口修正 `this` 后调用 `C::f()`。虚继承主要解决菱形继承中共同基类子对象重复的问题，不会自动消除两个不同基类的同名函数歧义；如果 A、B 虚继承共同基类，并且都重写了共同基类的同一个虚函数，C 还必须提供统一的最终重写，否则类定义不合法。

#### 构造函数能不能为虚函数，原因
构造函数不能声明为虚函数，因为虚函数调用依赖对象的虚函数表，而构造阶段对象还没有完成初始化。创建派生类对象时，首先构造基类部分，此时派生类部分还不存在，无法确定应该调用哪个派生类构造函数。

### vptr和它的初始化时机
如果一个类有虚函数，那么该类对象通常会包含一个 vptr（虚函数表指针）。vptr 由编译器在对象构造过程中进行初始化，使其指向当前正在构造层级对应的 vtable。

#### 析构函数内部调用虚函数行为
在析构函数中调用虚函数不会发生正常的多态调用，只会调用当前析构层级的函数版本。因为对象析构过程中，派生类部分已经开始销毁，vptr 会随着析构过程调整到当前类的虚表，避免调用已经不存在的派生类状态。

#### 1. unordered_map 的哈希计算细节是什么？结果就是地址吗？

##### 面试回答

`unordered_map` 的哈希函数把键转换成一个 `std::size_t` 类型的整数。**这个整数是哈希值，不是内存地址。**

容器根据哈希值确定元素属于哪个桶，再在桶内通过相等比较找到目标元素。

不同的键可能产生相同的哈希值，也可能映射到同一个桶，因此需要处理哈希冲突。

##### 哈希冲突怎么处理？

主流标准库实现通常使用节点和链式结构组织元素，逻辑上可以理解为：

```text
桶数组
┌───────┐
│ 桶 0  │ → 节点 A → 节点 B
├───────┤
│ 桶 1  │ → 空
├───────┤
│ 桶 2  │ → 节点 C
└───────┘
```

这是概念示意，实际实现不一定是每个桶各自维护一条独立链表。

查找步骤：

1. 根据键计算哈希值。
2. 确定对应的桶。
3. 检查桶中的候选元素。
4. 使用 `KeyEqual` 判断键是否相等。

默认的 `KeyEqual` 是 `std::equal_to<Key>`，通常会调用键类型的 `operator==`。

需要记住：

```text
键相等 → 哈希值必须相等
哈希值相等 → 键不一定相等
进入同一个桶 → 哈希值也不一定相等
```

良好的哈希分布使每个桶中的元素较少，所以查找平均为 `O(1)`；严重冲突时，最坏可能退化为 `O(n)`。

#### 2. map 为什么用红黑树？红黑树比 AVL 树好在哪里？红黑树是二叉搜索树吗？

##### 面试回答

`std::map` 通常使用红黑树实现，但 C++ 标准没有强制要求必须使用红黑树，而是规定了有序性、操作复杂度等要求。

**红黑树是具有额外平衡约束的二叉搜索树。**

它既满足二叉搜索树的顺序关系，又通过节点颜色和黑高约束，让树高保持在 `O(log n)`，从而保证查找、普通插入和按键删除的对数复杂度。

AVL 树的平衡条件更严格，通常树高更低，有利于查找。红黑树的平衡条件相对宽松，更新时通常需要较少的结构调整，尤其适合需要兼顾查找、插入和删除的通用有序容器。

不过，红黑树并不是所有场景都比 AVL 树快，实际性能还与数据分布、操作比例和实现方式有关。

##### 理解：它们的关系是什么？

```text
二叉搜索树 BST
├── AVL 树：严格平衡
└── 红黑树：通过颜色规则约束平衡
```

对于键唯一的二叉搜索树，可以将顺序关系理解为：

```text
左子树的键 < 当前节点的键 < 右子树的键
```

在 `map` 中，“小于”由比较器定义，不一定是数值大小。

普通二叉搜索树如果连续插入递增数据，可能退化成链表：

AVL 树和红黑树都通过维持平衡避免这种退化。

### AVL 树和红黑树的区别

| 对比项 | AVL 树 | 红黑树 |
|---|---|---|
| 平衡规则 | 每个节点左右子树高度差不超过 1 | 通过颜色和黑高规则限制树高 |
| 平衡程度 | 更严格 | 相对宽松 |
| 树高 | 通常更低 | 允许稍高 |
| 查找 | 更低的树高可能减少比较次数 | 同样保证 `O(log n)` |
| 插入、删除 | 可能需要更严格地恢复平衡 | 通常较少进行结构调整 |
| 适用倾向 | 查找密集的场景可以考虑 | 读写混合的通用场景很常见 |

红黑树的主要规则：

- 节点是红色或黑色。
- 根节点是黑色。
- 空叶子节点，也称 NIL 节点，是黑色。
- 红色节点不能有红色孩子。
- 从任一节点到其各个后代 NIL 节点的路径，黑色节点数量相同。

这些规则允许左右子树高度不同，但会限制差距，使树高保持在 `O(log n)`。

### 一个容易说错的细节

不要回答：

> AVL 树插入和删除都需要 `O(log n)` 次旋转，而红黑树只需要常数时间。

更准确的说法是：

- AVL 树插入通常只需在首个失衡祖先处做一次单旋或双旋，但仍可能需要沿路径更新高度。
- AVL 树删除可能导致多个祖先失衡，需要沿路径继续调整。
- 经典红黑树插入最多进行 2 次旋转，删除最多进行 3 次旋转，但重新着色和向上修复仍可能需要 `O(log n)` 时间。

**旋转次数较少，不等于整个插入或删除操作是 `O(1)`。**

#### 3. unordered_map 的迭代器稳定吗？稳定是什么意思？扩容是什么？

##### 面试回答

迭代器稳定，是指容器经过某些修改后，之前取得的迭代器仍然有效，可以继续用来访问原来的元素。

`unordered_map` 的迭代器是**有条件稳定的**：

- 插入元素但没有触发 rehash，已有迭代器仍然有效。
- 插入触发 rehash，所有已有迭代器都会失效。
- 删除元素，只会使指向被删除元素的迭代器失效。

扩容通常指增加桶数量并进行 rehash，也就是根据新的桶数量重新组织元素。

**rehash 会使迭代器失效，但不会使指向现存元素的指针和引用失效。**


##### 什么情况下会扩容？

有几个相关接口：

```cpp
m.size();            // 元素数量
m.bucket_count();    // 桶数量
m.load_factor();     // 当前负载因子
m.max_load_factor(); // 最大负载因子阈值
```

负载因子可以理解为：

```text
load_factor = 元素数量 / 桶数量
```

例如：

```text
元素数量 = 8
桶数量   = 10
负载因子 = 0.8
```

桶数量固定时，元素越来越多，平均每个桶需要处理的元素也会增加。

当插入使负载超过容器允许的阈值时，容器会增加桶数量，并重新组织元素：

```text
扩容前：桶较少，各桶可能比较拥挤
扩容后：桶更多，元素重新分布
```

##### 迭代器失效规则

| 操作 | 对已有迭代器的影响 |
|---|---|
| `find` 等查找操作 | 不失效 |
| 插入，未触发 rehash | 不失效 |
| 插入，触发 rehash | 全部失效 |
| `erase` | 只有被删除元素的迭代器失效 |
| `clear` | 所有元素的迭代器失效 |
| `rehash`、`reserve` | 应重新获取迭代器，不依赖操作前的迭代器 |

`operator[]` 也需要注意：

```cpp
m[key] = value;
```

如果 `key` 不存在，这个操作会插入元素，也可能触发 rehash。

##### 为什么迭代器失效，指针和引用却还能有效？

因为元素对象可以继续位于原来的内存位置，但桶结构和遍历关系已经改变。

struct Node {
    int key;
    int value;
    Node* next;
};

bucket数组里存放的是Node指针，实际上就是Node链表，每个节点是插入的时候new出来的，根据key算出哈希值，然后算出在bucket里应该插入到哪个位置的链表上然后插入的。
所以就算你rehash,有可能的是某些点的插入位置变了，不在原来bucket的idx所在的链表下了，但是new出来的那片内存空间没变，所以使用指向value的指针不变，引用也不变 所以指针和引用不会失效，只是不能通过原来的迭代器来访问value了。


##### reserve 和 rehash 有什么区别？

```cpp
m.reserve(1000); // 按当前最大负载因子，为容纳 1000 个元素准备足够的桶
m.rehash(1000);  // 请求至少 1000 个桶，同时满足现有元素的负载要求
```

记忆方式：

> `reserve` 的参数按元素数理解，`rehash` 的参数按桶数理解。

提前知道数据规模时，可以先 `reserve`，减少后续插入过程中的 rehash。最好在 `reserve` 之后再取得需要保存的迭代器。

#### 4. unordered_map 和 map 使用自定义类作为键

##### 面试回答

`unordered_map` 需要定义：

1. 如何计算键的哈希值。
2. 如何判断两个键相等。

必须满足：

> 如果两个键相等，它们的哈希值必须相同。

`map` 需要提供满足**严格弱序**的比较规则。它通过比较器判断键是否等价，不依赖 `operator==`：

```cpp
!comp(a, b) && !comp(b, a)
```

如果两个方向都不排在对方前面，`map` 就把它们视为等价键。

##### 完整示例

下面用姓名和年龄共同确定一个键：

```cpp
#include <cstddef>
#include <functional>
#include <iostream>
#include <map>
#include <string>
#include <tuple>
#include <unordered_map>

struct Person {
    std::string name;
    int age;

    // unordered_map 默认通过 std::equal_to<Person> 调用此比较。
    bool operator==(const Person& other) const {
        return name == other.name && age == other.age;
    }
};

struct PersonHash {
    std::size_t operator()(const Person& p) const {
        const std::size_t h1 = std::hash<std::string>{}(p.name);
        const std::size_t h2 = std::hash<int>{}(p.age);

        // 将两个字段的哈希值组合起来。
        // 哈希值不要求唯一，发生冲突后还会通过 == 判断。
        return h1 ^ (h2 + static_cast<std::size_t>(0x9e3779b9)
                     + (h1 << 6) + (h1 >> 2));
    }
};

struct PersonLess {
    bool operator()(const Person& a, const Person& b) const {
        // 先按 name 排序；name 相同时再按 age 排序。
        return std::tie(a.name, a.age) < std::tie(b.name, b.age);
    }
};

int main() {
    // 自定义哈希函数，使用默认的相等比较。
    std::unordered_map<Person, std::string, PersonHash> hash_map;

    hash_map.emplace(Person{"Alice", 20}, "Student");
    hash_map.emplace(Person{"Alice", 30}, "Engineer");

    if (auto it = hash_map.find(Person{"Alice", 20});
        it != hash_map.end()) {
        std::cout << it->second << '\n';
    }

    // 自定义排序规则。
    std::map<Person, std::string, PersonLess> tree_map;

    tree_map.emplace(Person{"Bob", 25}, "Designer");
    tree_map.emplace(Person{"Alice", 30}, "Engineer");
    tree_map.emplace(Person{"Alice", 20}, "Student");

    for (const auto& [person, job] : tree_map) {
        std::cout << person.name << ' '
                  << person.age << ": "
                  << job << '\n';
    }
}
```

`tree_map` 的输出顺序：

```text
Alice 20: Student
Alice 30: Engineer
Bob 25: Designer
```

##### 常见坑一：相等的键产生不同哈希值

例如，相等比较只看 `name`，哈希计算却同时使用 `name` 和 `age`：

```text
Alice, 20
Alice, 30
```

按照相等比较，这两个键相等，但它们可能产生不同哈希值，这违反了容器要求。

反过来，哈希只使用 `name`，相等比较使用 `name + age`，是合法的，只是可能产生更多冲突。

关键要求是：

```text
相等的键必须产生相同哈希值。
不相等的键允许产生相同哈希值。
```

##### 常见坑二：map 比较器只比较部分字段

如果比较器只比较姓名：

```cpp
return a.name < b.name;
```

那么：

```cpp
Person{"Alice", 20}
Person{"Alice", 30}
```

会被 `map` 视为等价键，不能作为两个不同的键同时保存。

比较器也不能简单写成 `<=`，因为严格弱序要求：

```cpp
comp(a, a) == false
```

##### 补充：键不能通过迭代器直接修改

`map` 和 `unordered_map` 的元素类型都是：

```cpp
std::pair<const Key, T>
```

因此：

```cpp
it->second = new_value; // 可以修改值
// it->first = new_key; // 不允许直接修改键
```

这是为了防止修改键后破坏排序关系或哈希桶归属。

#### 5. map 范围查询代码示例

##### 面试回答

`map` 按键有序，可以通过 `lower_bound` 和 `upper_bound` 确定范围边界。

默认升序比较时：

- `lower_bound(x)` 返回第一个键**大于等于 `x`** 的元素。
- `upper_bound(x)` 返回第一个键**大于 `x`** 的元素。
- 如果不存在符合条件的元素，则返回 `end()`。

例如查询闭区间 `[L, R]`：

```cpp
auto first = m.lower_bound(L);
auto last  = m.upper_bound(R);
```

遍历 `[first, last)` 即可。

定位边界需要 `O(log n)`，输出 `k` 个元素需要 `O(k)`，总复杂度是 **`O(log n + k)`**。

##### 完整示例：查询 [20, 40]

```cpp
#include <iostream>
#include <map>
#include <string>

void print_range(const std::map<int, std::string>& m,
                 int left,
                 int right) {
    if (left > right) {
        return;
    }

    auto first = m.lower_bound(left);
    auto last = m.upper_bound(right);

    for (auto it = first; it != last; ++it) {
        std::cout << it->first << ": " << it->second << '\n';
    }
}

int main() {
    std::map<int, std::string> m{
        {10, "A"},
        {20, "B"},
        {30, "C"},
        {40, "D"},
        {50, "E"}
    };

    print_range(m, 20, 40);
}
```

输出：

```text
20: B
30: C
40: D
```

即使边界本身不存在，也能正常查询：

```cpp
print_range(m, 21, 39); // 只输出 30: C
```

##### 为什么查询闭区间也使用半开迭代器区间？

要查询的键范围是：

```text
20 ≤ key ≤ 40
```

`upper_bound(40)` 指向第一个大于 `40` 的元素，即 `50`。

所以遍历过程是：

```text
20 → 30 → 40 → 到达 50 时停止
```

键的区间是闭区间 `[20, 40]`，但迭代器区间仍然是 `[first, last)`。

##### 不同区间的边界写法

以下针对默认升序的 `map`：

| 查询区间 | 起点，包含 | 终点，不包含 |
|---|---|---|
| `[L, R]` | `lower_bound(L)` | `upper_bound(R)` |
| `[L, R)` | `lower_bound(L)` | `lower_bound(R)` |
| `(L, R]` | `upper_bound(L)` | `upper_bound(R)` |
| `(L, R)` | `upper_bound(L)` | `lower_bound(R)` |

使用这些写法时，要先处理空区间：

- `L > R`：都为空。
- `L == R`：只有 `[L, R]` 可能包含元素，其余区间为空。

尤其是 `(L, R)`：如果 `L == R` 且该键存在，直接使用表中的两个迭代器会得到颠倒的边界，不能照常遍历。

例如：

```cpp
// 查询开区间 (left, right)
if (left < right) {
    auto first = m.upper_bound(left);
    auto last = m.lower_bound(right);

    for (auto it = first; it != last; ++it) {
        std::cout << it->first << '\n';
    }
}
```

##### 优先使用 map 的成员函数

应优先使用：

```cpp
m.lower_bound(x);
```

它能利用树结构，在 `O(log n)` 时间内完成查找。

不要直接替换为通用算法：

```cpp
std::lower_bound(m.begin(), m.end(), ...);
```

通用算法无法利用 `map` 的树结构。由于 `map` 的迭代器不是随机访问迭代器，虽然比较次数可以是对数级别，但迭代器移动次数可能达到线性级别。

##### 自定义比较器时的注意事项

“第一个大于等于”和“第一个大于”是针对默认升序比较的直观描述。

更一般地：

```text
lower_bound(x)：第一个满足 !comp(key, x) 的元素
upper_bound(x)：第一个满足 comp(x, key) 的元素
```

如果使用 `std::greater<Key>` 等降序比较器，就需要按照该比较器定义的顺序理解范围边界，不能直接照搬数值升序区间的写法。

#### malloc 底层实现原理
**简化流程：**

```text
malloc(size)
    ↓
调整大小：管理开销、内存对齐、最小块限制
    ↓
尝试复用已有内存块
    ├── 有合适的块 → 必要时拆分 → 返回用户区域指针
    │
    └── 空间不足 → 通过 brk / mmap 等获得更多空间
                    ↓
                  完成分配
```

**容易被追问的细节：**

- 多个 arena 和线程缓存可以降低多线程分配时的锁竞争。
- 不能死记“小于 128 KB 一定走 brk，大于 128 KB 一定走 mmap”，映射阈值可以调整，分配器也可能复用已有空闲块。
- 返回的是虚拟地址，不代表所有相关物理页都已立即分配；新映射中的页面可以在访问时按需准备。

#### malloc(1) 实际分配内存大小
`malloc(1)` 表示申请 1 字节的用户空间，但分配器实际管理的内存块通常更大，因为需要考虑管理信息、内存对齐，以及最小块大小。

具体大小由分配器和平台决定，不能脱离环境给出固定答案。

以常见的 **x86-64 Linux、glibc 默认实现**为例，内存通常按 16 字节对齐，最小 chunk 大小为 32 字节，因此 `malloc(1)` 通常会分配一个 **32 字节的 chunk**。

需要区分三个数字：

| 含义 | 常见结果 |
|---|---:|
| 程序申请的大小 | 1 字节 |
| `malloc_usable_size` 报告的可用大小 | 通常为 24 字节 |
| 分配器内部的 chunk 大小 | 通常为 32 字节 |

24 字节与 32 字节不矛盾：一个描述可用空间，另一个描述内部块大小；glibc 的相邻块还存在部分管理字段复用的布局设计。

**但程序应按申请的 1 字节使用，不能依赖额外空间进行越界访问。**如果需要更多空间，应申请相应大小，或者调用 `realloc`。

**查看当前实现报告的可用大小：**

```cpp
#include <cstdio>
#include <cstdlib>
#include <malloc.h>

int main() {
    void* p = std::malloc(1);
    if (p == nullptr) {
        return 1;
    }

    std::printf("requested: 1 byte\n");
    std::printf("usable: %zu bytes\n", malloc_usable_size(p));

    std::free(p);
}
```

`malloc_usable_size` 是实现相关接口，不是标准 C/C++ 接口，适合用于诊断和观察。

另外，`malloc(1)` 不代表操作系统为它单独分配一整个 4 KiB 页面。多个小内存块可以共享同一页；如果分配器需要扩展内存，也可能一次取得远大于 32 字节的空间。

#### #include <> 与 #include "" 的区别？标准库能否用双引号，自定义文件能否用尖括号？

**面试回答：**

两者主要区别在于**头文件的搜索规则**，不是强制区分标准库头文件和自定义头文件。

具体搜索路径由编译器实现和编译选项决定。以 GCC 的常见行为为例：

- `#include <xxx>`：从配置的头文件搜索路径中查找，包括 `-I` 指定的目录和系统头文件目录。
- `#include "xxx"`：先从包含这条指令的文件所在目录查找，再查找 `-iquote` 指定的目录，之后按尖括号形式使用的搜索路径继续查找。

因此：

- **标准库头文件可以使用双引号**，但通常推荐使用尖括号，表达意图，并减少被当前文件目录中的同名文件遮蔽的风险。
- **自定义头文件可以使用尖括号**，只要它所在的目录已经加入相应的头文件搜索路径，例如通过 `-I` 指定。

**一句话概括：**

尖括号和双引号决定搜索方式，不决定头文件的身份；标准库可以用双引号，自定义头文件也可以用尖括号，关键是搜索路径能否找到预期的头文件。

#### select、poll、epoll 的区别，以及各自适用的场景

### 面试回答

`select`、`poll`、`epoll` 都是 I/O 多路复用机制，用来让一个线程同时等待多个文件描述符上的就绪事件，例如 socket 可读、可写。

它们主要区别在于如何提交关注的文件描述符，以及如何发现和返回就绪事件：

- `select` 使用位图表示文件描述符集合，每次调用都需要传入集合，返回后还要检查哪些描述符就绪。Linux 下常用的 `fd_set` 存在 `FD_SETSIZE` 限制，通常只能处理编号小于 1024 的 fd。
- `poll` 使用 `pollfd` 数组，没有 `select` 的固定编号限制，但每次调用仍然需要提交整个数组并检查就绪情况。
- `epoll` 在内核中持久维护关注的描述符集合，通过 `epoll_ctl` 增删改，通过 `epoll_wait` 获取就绪事件，避免每次等待都重新提交和扫描全部关注对象。

因此，少量连接、兼容旧代码时可以使用 `select`；需要 POSIX 可移植性、连接数量不大时可以使用 `poll`；Linux 下大量连接，尤其是大量空闲连接、少量活跃连接的场景，通常适合使用 `epoll`。

调用性能上: select 接口和 poll 要分别拷贝fd_set和 pollfd数组到内核， 但是epoll 机制把拷贝结构的操作放到了epoll_ctl， epoll_wait没有拷贝
用户态数组到内核的这个操作。这是一个性能优势。
另外假设poll有10w个连接，里面只有一个连接活跃，那也要拷贝十万个数组内容到内核，然后poll结束之后用户态程序还需要遍历10万个连接看看哪个是活跃的。


### 1. 核心对比

设：

- `N`：监听的 fd 数量。
- `M`：最大 fd 编号加 1。
- `K`：本次返回的就绪事件数量。

| 对比项 | select | poll | epoll |
|---|---|---|---|
| 接口中的关注集合 | `fd_set` 位图 | `pollfd` 数组 | 内核维护的关注集合 |
| 每次等待是否提交完整关注集合 | 是 | 是 | 否，通过 `epoll_ctl` 单独更新 |
| 获取就绪结果 | 检查返回的位图 | 遍历数组中的 `revents` | 遍历返回的就绪事件 |
| 主要扫描开销 | 与 fd 编号范围 `M` 有关 | 与数组长度 `N` 有关 | 获取结果主要与就绪数量 `K` 有关 |
| 固定 fd 编号限制 | 常见 glibc 环境要求 fd 小于 1024 | 没有这种固定限制 | 没有这种固定限制 |
| 输入集合是否被改写 | 会，需要恢复 | `events` 保留，结果写入 `revents` | 不需要每轮重建关注集合 |
| 触发方式 | 类似水平触发 | 类似水平触发 | 默认 LT，也支持 ET |
| 可移植性 | POSIX 接口 | POSIX 接口 | Linux 特有接口 |

注意：`poll`、`epoll` 也不是无限制，仍然受进程 fd 限制、内存等资源约束。

### 2. 为什么大量空闲连接时 epoll 更有优势？

假设服务器保持了 10 万个连接，但本轮只有 10 个连接有数据。

`poll` 的处理方式可以理解为：

```text
把整个关注数组传给内核
    ↓
内核检查数组中的描述符
    ↓
返回后，用户程序扫描数组
    ↓
找出就绪的 10 个连接
```

`epoll` 的处理方式可以理解为：

```text
提前把连接注册到 epoll
    ↓
内核通过事件通知机制维护就绪状态
    ↓
epoll_wait 返回本轮的就绪事件
    ↓
用户程序处理返回的 10 个连接
```

区别在于：`epoll` 不需要为了发现少量就绪连接，每轮都把所有空闲连接重新检查一遍。

但不能简单说：

> epoll 所有操作都是 O(1)。

注册、删除、状态维护、事件传递都有成本，返回和处理 K 个事件至少需要与 K 相应的工作量。

### 3. 各自适合什么场景？

| 场景 | 通常选择 | 原因 |
|---|---|---|
| 维护已有的 select 程序，fd 很少且编号符合限制 | select | 改动少，足以满足需求 |
| 小型客户端，只关注少量 socket、管道等 | poll | 接口直接，没有 select 的固定 fd 编号限制 |
| 需要在多个 POSIX 系统之间移植 | poll，或平台抽象库 | epoll 不是通用 POSIX 接口 |
| Linux 高并发服务器，大量连接长期存在 | epoll | 关注集合可复用，适合大量空闲连接 |
| Linux 网关、聊天服务、长连接服务 | epoll | 通常只有部分连接在某个时刻活跃 |
| fd 很少、关注集合频繁变化 | poll 往往足够 | 扫描成本低，避免额外维护注册状态 |

**epoll 不一定在所有场景中都最快。**

如果 fd 很少，或者几乎全部连接一直活跃，`poll` 的扫描成本可能并不突出。`epoll` 也需要维护内部状态，并在增删改监听时执行额外操作。最终应结合实际负载判断。

### 4. epoll 的 LT 和 ET 有什么区别？

**LT：水平触发，默认模式。**

只要就绪条件仍然成立，后续等待仍然可以返回该事件。

例如接收缓冲区有 100 字节，你只读了 20 字节，剩下的 80 字节仍然使 socket 可读，之后还会得到可读通知。

**ET：边沿触发。**

围绕新的就绪变化进行通知，不能指望“上次没读完的数据”一定让下一次 `epoll_wait` 再返回事件。

因此，常规 ET 写法应当：

- 使用非阻塞 socket。
- 收到读事件后，持续读取，直到 `EAGAIN/EWOULDBLOCK`，或者遇到 EOF、错误。
- 写入时持续处理待发送数据，直到全部发送完，或者遇到 `EAGAIN/EWOULDBLOCK`、错误。

ET 对状态管理要求更高，不代表一定比 LT 快。多数场景可以先使用 LT，确认瓶颈后再考虑 ET。

### 5. 面试容易说错的地方

**第一，select 的限制不只是“连接数最多 1024”。**

更准确地说，常见 glibc 的 `fd_set` 只能表示编号小于 `FD_SETSIZE` 的 fd。

即使只监听一个 socket，如果它的 fd 编号已经是 2000，也不能直接放进这样的 `fd_set`。

**第二，epoll 不是异步 I/O 完成通知。**

它告诉程序的是“现在可以尝试读写”，不是“已经替你完成了读写”。

程序仍然需要调用：

```cpp
recv(...);
send(...);
```

**第三，就绪不保证后续操作永远不会阻塞。**

状态可能被其他线程改变，一次较大的写入也可能无法全部完成。因此，事件循环中的网络 socket 通常配合非阻塞模式使用，并正确处理 `EAGAIN/EWOULDBLOCK`。

**第四，不能长期无条件监听可写事件。**

socket 经常处于可写状态。LT 模式下如果一直监听可写事件，即使没有数据要发送，也可能不断被唤醒。

常见做法是：有待发送数据且暂时写不完时关注可写事件，发送完后取消对应关注。

2. C++ 中 new 和 malloc 的行为有什么不同？分别适合什么场景？


new 是 C++ 运算符，会分配内存并调用对象的构造函数；delete 会先调用析构函数，再释放内存。malloc 和 free 是 C 风格的内存管理函数，只负责申请和释放原始内存，不会自动构造或析构对象。

struct Item {
    Item() { /* 初始化资源 */ }
    ~Item() { /* 释放资源 */ }
};

Item* a = new Item;
delete a;

void* raw = std::malloc(sizeof(Item));
if (raw != nullptr) {
    Item* b = new (raw) Item;  // placement new
    b->~Item();
    std::free(raw);
}
使用 malloc 申请的内存应由 free 释放；使用普通 new 申请的对象应由 delete 释放，不能混用。

3. shared_ptr 的引用计数为什么通常不会因为对象销毁而归零？它的控制块通常保存什么？
shared_ptr 通常通过独立的控制块管理对象生命周期。控制块一般包含强引用计数、弱引用计数、删除器，以及对象指针或管理对象所需的信息。强引用计数归零时，对象被销毁；弱引用计数归零时，控制块才会释放。

如果两个 shared_ptr 通过不同控制块管理同一个裸指针，可能导致重复释放。需要从同一个 shared_ptr 派生所有共享所有权，不要对同一个裸指针分别构造多个 shared_ptr。

4. 什么情况下应选择 unique_ptr 而不是 shared_ptr？unique_ptr 如何转移所有权？
当资源只有一个明确所有者时，应优先选择 unique_ptr。它不维护共享引用计数，所有权通过移动操作转移；移动后，源指针为空。unique_ptr 也可以通过自定义删除器管理文件句柄等非内存资源。

auto first = std::make_unique<int>(42);
auto second = std::move(first);

if (!first) {
    // first 已不再拥有对象
}
5. weak_ptr 怎样判断共享对象是否仍然存活？为什么它不能直接访问对象？
weak_ptr 不增加强引用计数，因此不会阻止对象销毁。调用 lock() 可以尝试取得临时的 shared_ptr：若对象仍存活，返回非空指针；否则返回空指针。直接通过 weak_ptr 访问对象不安全，因为对象可能已经销毁。

它常用于打破 shared_ptr 形成的循环引用，例如父子对象关系中让子对象对父对象持有弱引用。

6. shared_ptr 的引用计数线程安全，是否意味着多个线程可以安全地修改同一个 shared_ptr 变量？
不一定。不同 shared_ptr 实例共享控制块时，引用计数的增减通常是线程安全的；但多个线程无同步地读写同一个 shared_ptr 变量，仍可能发生数据竞争。C++20 可使用 std::atomic<std::shared_ptr<T>>，也可以用互斥锁保护该变量。

此外，引用计数线程安全不代表被管理对象的成员访问线程安全，仍需为对象状态设计同步机制。

7. new 表达式在构造函数抛出异常时会发生什么？如果使用 placement new 又有什么不同？
普通 new 表达式先分配内存，再构造对象。构造函数抛出异常时，编译器会调用相应的释放函数回收已分配的内存。

placement new 只在指定地址上构造对象，不负责申请底层内存，因此构造失败时不会释放那块内存。底层存储需要由原所有者继续管理；若构造成功，还需显式调用析构函数。

8. std::move 会移动对象吗？它的实际作用是什么？
std::move 本身不执行资源搬运，它将表达式转换为右值引用类型，使重载决议可以选择移动构造函数或移动赋值运算符。对象是否真的移动，取决于目标类型是否提供可用的移动操作。

std::string source = "data";
std::string target = std::move(source);
移动后的 source 仍处于有效但状态未指定的状态，可以重新赋值或执行该类型允许的操作，不应假定它仍保存原内容。

9. 如果某个类定义了析构函数，却没有显式声明移动构造函数，编译器一定会生成移动构造函数吗？
不一定。用户声明析构函数、拷贝构造或拷贝赋值等特殊成员函数，会影响移动操作的隐式生成。若类需要移动语义，应明确检查并声明移动构造和移动赋值；若资源所有权不应被复制，则通常删除拷贝操作。

class Buffer {
public:
    Buffer(const Buffer&) = delete;
    Buffer& operator=(const Buffer&) = delete;

    Buffer(Buffer&&) noexcept = default;
    Buffer& operator=(Buffer&&) noexcept = default;

    ~Buffer() = default;
};
10. static_cast、dynamic_cast、const_cast 和 reinterpret_cast 的适用边界是什么？
static_cast 用于编译期可检查的类型转换，例如数值转换或已知的基类、派生类转换。dynamic_cast 用于多态类型的运行时向下转型，失败时指针转换返回 nullptr，引用转换抛出 std::bad_cast。const_cast 用于添加或移除 const、volatile 限定，但修改原本定义为 const 的对象属于未定义行为。reinterpret_cast 用于低层、平台相关的重新解释，不会验证数据布局或对象有效性，应谨慎使用。

11. dynamic_cast 为什么要求源类型通常是多态类型？它和 static_cast 的安全性差异在哪里？
运行时向下转型需要对象携带可用于运行时类型识别的信息。多态类通过虚函数机制支持这类检查；若目标类型不匹配，dynamic_cast 能报告失败。

static_cast 不进行运行时验证。若实际对象不是目标派生类型，却强行向下转换并访问派生类成员，行为可能未定义。对象类型关系由程序逻辑严格保证时可以考虑 static_cast；类型不确定时应使用 dynamic_cast 或改为设计更清晰的接口。


14. 对象内存对齐会影响结构体大小吗？如何分析一个结构体的布局？
会。成员通常需要满足各自的对齐要求，编译器可能在成员之间和结构体末尾插入填充字节。结构体大小通常是最大成员对齐要求的整数倍。具体布局可能受 ABI、编译器和平台影响，应使用 sizeof 和 alignof 验证。

#include <iostream>

struct Record {
    char flag;
    double value;
    int count;
};

int main() {
    std::cout << sizeof(Record) << '\n';
    std::cout << alignof(Record) << '\n';
}
将较大对齐要求的成员放在前面，通常可以减少填充，但不能把这种排序当作跨平台布局保证。

15. 在 32 位与 64 位环境中，对齐和指针大小会带来哪些影响？
常见平台上，指针在 32 位环境中为 4 字节，在 64 位环境中为 8 字节，但具体仍由平台 ABI 决定。指针变大可能改变包含指针的结构体大小、内存占用和缓存行为。不同平台的基本类型大小、最大对齐要求也可能不同，因此不能仅凭“64 位”推断所有类型的精确布局。

对于网络协议或文件格式，不应直接写入本机结构体内存；应明确字段宽度、字节序和序列化规则。

16. std::vector 扩容时哪些操作可能使已有迭代器、指针和引用失效？
如果扩容导致重新分配，指向元素的指针、引用、迭代器都会失效。若没有重新分配，在末尾插入通常会使 end() 失效，但已有元素的引用和迭代器一般保持有效；在中间插入或删除时，受影响位置及其之后的元素引用和迭代器可能失效。

若能预估元素数量，可提前调用 reserve() 减少扩容次数，但不能因此假设后续插入永远不会发生重分配。

17. 实现一个拥有动态数组的容器时，为什么复制构造和复制赋值要考虑自赋值及异常安全？
容器拥有资源时，浅拷贝会让多个对象指向同一块内存，最终可能重复释放。复制赋值还要处理 x = x；直接先释放旧资源再分配新资源，一旦分配失败，左侧对象可能已丢失原状态。

一种简单做法是先构造临时副本，再交换资源，这样分配或复制失败时原对象保持不变。

18. MyVector 的移动构造和移动赋值应如何处理资源所有权？
移动构造可以接管源对象的指针、大小和容量，再将源对象重置为空状态。移动赋值还要先妥善释放当前对象所拥有的资源，并处理自移动赋值。若移动操作不会抛异常，应标记为 noexcept，有利于标准容器在扩容时选择移动元素。

#include <algorithm>
#include <cstddef>
#include <utility>

class MyVector {
public:
    MyVector() = default;

    MyVector(MyVector&& other) noexcept
        : arr_(std::exchange(other.arr_, nullptr)),
          size_(std::exchange(other.size_, 0)),
          capacity_(std::exchange(other.capacity_, 0)) {}

    MyVector& operator=(MyVector&& other) noexcept {
        if (this != &other) {
            delete[] arr_;
            arr_ = std::exchange(other.arr_, nullptr);
            size_ = std::exchange(other.size_, 0);
            capacity_ = std::exchange(other.capacity_, 0);
        }
        return *this;
    }

    ~MyVector() {
        delete[] arr_;
    }

private:
    int* arr_ = nullptr;
    std::size_t size_ = 0;
    std::size_t capacity_ = 0;
};
19. std::vector 扩容时，为什么元素的移动构造最好是 noexcept？如果移动可能抛异常会怎样？
扩容需要把旧缓冲区中的元素转移到新缓冲区。如果移动构造可能抛异常，转移一部分元素后失败，可能难以恢复原容器的状态。标准容器通常会在类型支持时优先移动，否则可能选择拷贝，以维持异常保证。

因此，自定义资源类型在移动操作确实不会抛异常时应声明 noexcept；不能仅为触发移动而虚假标注，否则异常逃出 noexcept 函数会导致程序终止。

20. 如何为一个只允许移动、不允许拷贝的资源包装类设计接口？
删除拷贝构造和拷贝赋值，显式提供移动构造和移动赋值，并在析构函数中释放资源。移动之后，源对象必须处于可安全析构、可重新赋值的状态。资源释放逻辑最好集中在一个可靠的 RAII 包装类型中，避免手动管理散落在多个调用点。

21. 什么是严格别名规则？为什么通过不兼容类型的指针读取同一块内存可能产生未定义行为？
严格别名规则约束了程序可以通过哪些类型访问一个对象的存储。编译器会据此进行优化，因此将某类型对象的地址强行转换为不兼容类型指针并读取，可能导致未定义行为。需要查看对象表示时，可使用 std::memcpy，或在 C++20 中使用 std::bit_cast。

#include <bit>
#include <cstdint>

float value = 1.0f;
std::uint32_t bits = std::bit_cast<std::uint32_t>(value);
这要求目标和源类型大小相同且满足 bit_cast 的类型约束，但不能据此假定不同平台的浮点表示完全一致。

22. 什么情况下对象的生命周期会先于其存储空间结束？这种情况会影响哪些操作？
对象生命周期与存储空间的分配并不总是完全重合。例如，使用 placement new 在已分配的缓冲区中构造对象时，缓冲区可以继续存在，而对象生命周期在显式析构后结束。对象生命周期结束后，不能像原对象仍然存活那样读写其成员；若要在该位置创建新对象，需正确启动新对象的生命周期并遵守对齐要求。
